SiegeEngine is a custom C# engine for real-time multiplayer MMORPG-style games. Castle is the self-hosting IDE built on that same engine. Rendering, the asset pipeline, entities and components, EventBus, GameSystems, scenes, and the HTML/CSS/JS UI are one runtime used both to play a game and to build one. The editor is not a second product sitting beside the engine. Every system that runs a game is the system that authors it, so the tool is self-moddable and game-making itself is meant to feel like a meta-game: docked tools, live previews, instant Play, no steep toolchain, no mod-conflict tax, and multiplayer that is not an afterthought. Creators can be one person or a community. The application is supposed to behave like a professional creator tool, modular and secure, not like a prototype that never grew an editor.

The stack is four concerns that share a runtime and stay out of each other’s types. Core is the foundation used by gameplay and by the editor: abstracted rendering (OpenGL now, with room for DirectX and Vulkan), the FBX asset pipeline for meshes, skeletons, animations, materials, and textures, Entity/Component with parenting and delta tracking, a central EventBus of strongly typed networked events, GameSystems for per-frame work, scene management, a production-grade HTML/CSS/JS UI with data-hooks, mod loading, and Steam networking. The editor layer runs that engine in editor mode: dockable snapping panels, context blades, project and scene management, asset browser, properties, hierarchy, brushes, animation timeline and blend, in-panel 3D overlays, console. The server layer is authoritative validation, spatial grids, occlusion, movement and inventory and combat checks, entity deltas, and broadcast; the same server code can run dedicated, hybrid, or in editor collaboration. The bootstrap layer starts Steam, finds local and Workshop mods, builds context, loads settings, and runs the loop. All of those layers share rendering, assets, events, UI, and scenes on purpose so the IDE can be extended the same way a game is extended.

The boundary is the thing that must not drift. IDE code (CastleBuilder, BlueprintManager, MenuCommands, ProjectSettings, Keystone, ToolChest, MapRoom) may read and write disk, save projects, and emit payloads. Core (SiegeEngine, Foundation, Launcher, RuntimeGameplayScene, SceneContext) must never read ProjectSettings, Keystone, or any IDE type. Core does not know what a project is. It receives serialized Level and SceneData through a payload or through a SceneContext composed inside Core. Level is the in-memory source of truth for entities, terrain, skybox, environment, and custom data. The folder on disk is persistence and Export only. Play is in-memory. Export follows the same activation path and then copies assets. EventBus is the single communication path for UI to code, client to server, editor to runtime, and mod hooks. Mods override or extend through JSON and fully qualified hooks. Networking is P2P, hybrid, or dedicated from the same codebase. A panel contract in Core, if one is added, is named for what it does (content, HUD, hosted view), never for “project.” The host supplies chrome. Game assemblies supply content. Core stays ignorant of CastleBuilder and of project folders.

FlyCameraController, AngledOrthoCamera, and cameras like them are Core runtime cameras, not IDE-only toys. They are optional views: preview an environment while a level loads, free-look on a death screen, inspect a space without possessing a body. They must not be treated as PlayerMovement and they must not be banned from runtime. Movement is a separate system (PlayerMovement or a game-supplied controller such as TestSlideController). A runtime scene may have a fly camera, a player controller, both, or neither, depending on the mode. Do not wire the fly camera as the walk implementation, and do not delete it from runtime to “keep editor cameras out.”

Rendering, assets, EventBus, mod load, server validation, delta compression, and the terrain editor are treated as production-ready. The docked IDE with live resize and pop-outs is usable. Work from here is incremental and must keep that compartmentalization. Play Host builds a SceneContext in-process. Isolated Play launches Foundation with a payload. Those two are supposed to activate the same scripts, the same controller, the same scene, and later the same hosted HUD. Export is supposed to be that Play path plus assets, not a third command line.

You inspect the GitHub repository yourself. You do not clone onto the user’s machine, you do not commit, you do not push, and you do not edit their working tree. You read the named branch, you decide the change from the files that are actually there, and you return a zip of complete files only, each at its repo-relative path, so the folder can be dropped on the project root. Output only files you change. Full files, never snippets. No renamed variables, no extra features, no decorative logs, no drive-by cleanup. If a type or call path is unclear, stop and name the file you need instead of inventing a neighbor. Keep Core, IDE, game assemblies, Server, and Launcher on their own sides of the line. IDE assemblies must not reference each other across the CastleBuilder wall when that wall already exists. Prefer a small future-proof contract over a bandage in one panel. When a checkpoint is confirmed, treat that behavior as the new floor and do not reopen it.
