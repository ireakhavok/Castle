As a user building a game in SiegeEngine IDE, the entire experience is designed to feel like a professional, self-contained creative studio that is also the game itself. You start by creating a new project through the clean modal in the File menu. This instantly sets up a folder structure with project.json, Scenes, Assets, and Mods directories, and automatically gives you a default "Main" scene inside the project data. Every project is built around a collection of scenes, where each scene is a complete, self-contained world that can hold terrain data (heightmap + color texture + normal texture), a list of placed 3D entities (models, sprites, lights, future sound emitters), and environment settings (time of day, weather, ambient lighting). The system is deliberately 3D-first but flexible enough for 2D or hybrid workflows because the vifewport mode lives inside the runtime scene classes rather than being locked in the data.

The IDE itself is the editor. You see a slim top bar with context blades (Terrain, Animator, Scene Editor, Configuration) that instantly change the available tools and workspace focus. Clicking a blade publishes a context change event, which swaps panel layouts and, when you’re in Scene Editor, ensures a scene exists so you can immediately start building. The Panels dropdown always shows the right tools for the current blade (Terrain Creator for sculpting, Hierarchy and Properties for editing entities, etc.). Everything is saved automatically into the single project.json for now (we plan to split scenes into individual .scene.json files later for better Git and modding support), and the BlueprintManager handles loading, saving, and scene creation so your work persists between sessions.

Right now the system is at a solid but transitional stage: New Project and New Scene both work and create real data, the EditorScene panel opens and renders, and the context blades switch the UI layout correctly. However, the actual connection between the data model (SceneData) and the runtime scenes (TerrainCreatorScene, future full SceneEditor, etc.) is not yet live. When you switch to Scene Editor or create a new scene, you don’t yet see your terrain or entities appear in the 3D viewport, and changes you make in the terrain brush or entity placement tools do not yet write back into the SceneData.

We have been working to make the editor feel more connected and professional by linking the live 3D viewport where you sculpt terrain, place objects, and test things with the actual project data that the user creates and saves. Originally the visual tools and the saved project information were mostly separate, so loading a project didn't reliably bring your terrain or scene content into the viewport, and any changes you made while editing stayed only in the current session. The overall plan was to introduce a clean two-layer structure for scenes so the editor could behave like a real game while still staying tightly tied to the saved project file.

So far we have completed the first two foundational steps. In the first step we added a new higher-level game scene layer that sits above the basic engine scene. This game scene carries the real project data for each scene in the user's game, giving us a clean place to hold terrain settings, environment details, and any other content without touching the low-level rendering code. In the second step we updated the terrain editing view so it now uses this new game scene layer. When you load a project and open the scene editor panel, it automatically pulls the scene data from the project and loads the terrain into the 3D viewport. All the brush tools, ghost preview, sculpting, and rendering continue to work exactly as they always did — we kept every line of the existing terrain logic untouched and only added the one-time loading step that brings in the saved settings. Right now everything is still purely in memory, with no disk writes happening, and the editor gracefully handles the case when no project is loaded at all.

The next steps will continue closing this loop in small, safe increments. We will first make sure the user can easily select and switch between multiple scenes inside the same project through the existing editor interface. Then we will allow any modifications made while editing (such as brushing terrain) to be stored in the in-memory game scene data object. After that we will hook up the explicit Save Project command so that when the user chooses to save, the current live scene data is written back to the project file and any terrain files are placed into a proper subfolder inside the project directory. Later we will integrate the hierarchy and properties panels so they can see and edit the entities list inside the active game scene. Throughout all of these changes we must carefully respect the existing pattern used by other panels in the editor, where a runtime scene and its UI overlay already live together inside the same panel class. This keeps the dockable, resizable, and snapping behavior of the entire IDE stable and consistent while we add the new data-binding features.
