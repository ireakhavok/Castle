The IDEDockingStrategy is the central class that owns the entire IDE-style docking and layout system. It maintains a recursive tree composed of DockSplitNode (for horizontal or vertical splits with live SplitRatio) and DockTabbedNode (for tabbed panels) objects. Its responsibilities include processing all mouse input with absolute priority ordering (splitter dragging always takes precedence over title-bar drags, close-button clicks, or resize grips), performing pre-input and post-input layout computations so that every panel’s Rect, Position, and Size stay synchronized in real time, managing protected paths such as title-bar tear-out to floating state and close-button guards, and driving the final rendering pass that positions every panel on screen. It also handles floating panel lists, hover icon detection for docking, and tree collapsing after panels are removed or torn out.

The strategy is currently in a stable and mostly functional state for the majority of editor operations. Vertical splitter dragging works with immediate, flicker-free visual feedback at any nesting depth. Floating panels move, snap, and restore their original sizes correctly. Non-scene panels (pure UI panels without an inner scene) resize and render at the proper horizontal and vertical offsets even while the mouse is actively moving. The splitter drag path correctly owns the mouse for the entire duration of the drag, the layout tree updates SplitRatio live without snap-back, and all position/size values propagate correctly according to console logs and docking tree traversal.

The specific problem is isolated exclusively to panels that inherit from BasePanel but also contain an inner scene (TwoDCreatorPanel and its siblings). These panels provide their own Render() override that manually computes a content-area rectangle, sets a scissor rectangle, calls the scene’s Render method, then calls base.Render(). During live horizontal splitter dragging—while the mouse button remains held down and the mouse continues to move—the entire panel (title bar, close button, UI overlay, borders, and the scene content) renders at an incorrect horizontal offset, creating visible flickering or a stale position (frequently appearing shifted left toward X=0 or a previous frame’s value). The moment the mouse button is released, the panel instantly corrects to the proper final location. This behavior does not occur on vertical drags, does not affect non-scene panels, and is not present in the layout or position data itself (Position.X and scissor values update correctly per logs). The discrepancy appears only in the final rendering pass and only when the panel’s custom Render() override is active during horizontal live splitter movement.
