Recently we have updated the idebasepanelui.html. The IDE page now has a new set of context blades positioned horizontally along the right side of the existing top navigation bar, placed immediately next to the SiegeEngine IDE title text. These blades serve as the primary way for users to switch between major workflows inside the editor. The blades themselves are Terrain, Animator, Scene Editor, and Configuration. Clicking any one of them highlights the active blade with a distinct visual state and triggers a context switch that affects both the central workspace content and the items visible in the top menu bar. The Panels menu option remains exactly where it is today inside the main top navigation bar and continues to list all available panels that can be opened for that context, with the specific list of options inside it updating dynamically based on the currently active context blade.

A new event called ContextChangedEvent will be created inside the CastleBuilder.Events namespace and will follow the exact same strongly-typed pattern already used by NewProjectEvent, LoadProjectEvent, and SaveProjectEvent. This event carries only the name of the newly selected context and is published whenever a user clicks one of the right-side blades. No other namespaces or core engine files will be modified to support this system. MenuCommands.cs will be updated to subscribe to the new event and forward the context name to a dedicated SwitchContext method that lives entirely inside CastleBuilder. The existing IDEBasePanel and the menu bar rendering logic will listen for this event and adjust the visibility of top-menu items accordingly so that only the commands relevant to the active context appear. For example, when the Terrain blade is active the top menu will show additional Terrain-specific options in a context menu such as Sculpt, Brush Settings, Export Heightmap, and Import GeoTIFF, while when the Animator blade is active it will show Animation-specific options such as Import FBX, Blend Editor, Preview in Scene, and Animation List. I am just giving examples, and the actual examples will be determined at this point. 

The idedockingstrategy contains information that will be needed to save off the active and inactive panel configurations, so that the configuration of where the panels exist, what is loaded in those panels, and etc. are saved off and can by re-loaded. 

The central workspace of the IDE will respond to each context switch by loading the appropriate panels of the docking strategy that was last used for that particular loaded Editor Scene (allowing you to modify the terrain of the editor scene on the fly, then switch back to the editor scene that uses that same data). When the Scene Editor blade is selected the central area switches to the new WarTable.EditorScene, which reads the current project’s project.json file, presents a list or dropdown of all GAME scenes defined in the Scenes array, and loads only the terrain and entities belonging to the currently selected GAME scene. The Terrain blade switches the central area to the existing MapRoom.TerrainCreatorScene with its full sculpting tools. The Animator blade switches the central area to the ReadingChamber animation viewer. The Configuration blade switches the central area to a project-level settings view that includes server rules, mod management, and blueprint governance. Some panels will be permanently associated with specific contexts and will be decided later, while others such as TreeViewPanel and PropertiesPanel remain fully reusable and can appear in multiple contexts depending on what the user opens from the Panels menu.

BlueprintManager will be updated so that loading or creating a project automatically opens the Scene Editor blade and its corresponding WarTable.EditorScene by default, ensuring the multi-GAME-scene nature of projects is immediately visible and functional. The iterative implementation will proceed in small, isolated steps. Step 1 adds only the right-side blades to IDE_UI.html along with basic click handling that publishes the ContextChangedEvent and provides visual highlighting. Step 2 creates the ContextChangedEvent.cs file and wires the subscription inside MenuCommands.cs. Step 3 extends the menu bar logic to show or hide the correct context-specific items. Step 4 introduces the WarTable.EditorScene.cs file that handles loading individual GAME scenes from the project.json. Step 5 adds the automatic panel visibility behavior tied to each context switch. Each step will be self-contained, testable, and limited to files inside the CastleBuilder namespace so that another developer can continue directly from any point in the sequence without needing additional context beyond this description.

When the user switches blades (different editor modes/contexts — e.g. Terrain blade ↔ 2D blade ↔ Animation blade ↔ Properties blade, etc.), the current docking layout (split ratios, open panels, tab order, floating panel positions/sizes, etc.) is immediately saved to a temporary file (<projectName>.layout.temp).
This temp file acts as an “unsaved workspace” buffer.
Only when the user does an explicit SaveProject / SaveProjectAs does the temp file get promoted/merged into the main project save file.
On LoadProject, if a .layout.temp file exists for that project, show a user prompt:
“A previous unsaved workspace layout was found. Restore it?” (Yes / No / Discard)
This gives the same safety/recovery feel as modern IDEs (like Unity, Visual Studio, Rider) while supporting multiple “blades”.

We have reached a point where the blade system is partially functional. The four context blades in IDE_UI.html correctly publish ContextChangedEvent on click, MenuCommands routes them, and BlueprintManager.OnContextChanged fires every time. SaveCurrentLayout now writes layout.{Context}.json files to the project folder when a project is loaded, and the serialization in IDEDockingStrategy captures the root tree and some basic structure. IDEBasePanel listens for the event and refreshes the top menu. However, the restore side is completely broken. LoadLayoutForContext reports success in the console and calls DeserializeState, but nothing visually changes—the workspace stays empty after the clear, no panels reappear, and floating panels are never restored to their saved positions and sizes. Only split ratios are being saved; the full multi-level nested docking tree with mixed horizontal and vertical splits at arbitrary depths is lost. Floating panel information (type, position, size) is not captured at all. When no project is loaded, clicking any blade throws a null path exception in BlueprintManager.OnContextChanged because Path.Combine is called without checking ActiveProject. The user has reverted all recent aggressive clearing changes because they made behavior worse than before, so we are back at the version where saving works reliably but loading does nothing visible.
The overarching goal is still the same as originally planned: each blade (Terrain, Animator, Scene Editor, Configuration) must instantly save the complete current workspace layout when switching away from it and fully restore the exact saved layout when switching to it. This includes every nested split ratio, every tab order, every floating panel with its precise position and size, and every open panel. On project load, the LastContext from project.json should automatically restore the correct workspace. When no project is open, the system should silently fall back to a global temp folder in AppData without crashing or showing errors. A blade is never supposed to load an entire Scene object; it is only supposed to load and apply an entire saved docking strategy layout from IDEDockingStrategy.
We are now strictly focused on fixing the restore path before doing anything else.
