
Working brief – Scene / Level / SceneSettings architecture

We are working on the fundamental scene configuration and data-transfer architecture of SiegeEngine. The goal is to give every Scene a clean place for both its world content and its high-level game settings, while remaining fully modular for games that need almost nothing (chess, puzzle games, etc.) and while still allowing unsaved editor changes to reach the engine on Play.

The feature we are introducing and correcting is the relationship between Scene, Level, SceneSettings, and the payload that is handed to the core engine at Play / Export time. The intended hierarchy is:

text

Scene                          ← the top-level container the creator opens and loads
├── SceneSettings              ← optional player/avatar reference, dynamic controller reference,
│                                game-mode, input bindings, enabled systems, etc.
└── Level                      ← world content only
    ├── Entities               ← props, spawn points, lights, triggers…
    ├── Terrain                ← TerrainData (paths + settings only)
    ├── Skybox
    └── Environment

Heavy binary data (heightmaps, color textures, splat maps) continue to live as external files under Assets/Terrain/…. TerrainData only stores the paths and settings. The playable character is never stored as an ordinary Entity inside the Level; it exists only as a reference inside SceneSettings. At Build / Play time the engine reads that reference, loads the user-supplied controller and avatar pack, and spawns the player at a Spawn Point that does exist as a normal Entity in the Level. Controllers remain completely dynamic — the creator supplies them; the engine never hard-codes controller types.

What is currently implemented:

Level is the rich live object that holds real Entity instances (with components), Terrain, Skybox, Environment and CustomData.

SceneData is a DTO that is written into project.json. On save, BlueprintManager copies the live Level into SceneData.

PlayGame / ExportGame currently builds both a Level.Serialize() payload and a SceneData payload and passes both as base64 strings to the runtime.

The runtime prefers the reconstructed Level when it is supplied via SceneContext.

LiveSceneState correctly holds only the temporary working heightmap / ColorBitmap / Skybox for live painting and is never part of the core payload.

The existing Place-Entity / FileSelector path already mutates the live Level and can sync it to the editor server.

What is currently wrong or incomplete:

There is still a dual structure (Level vs SceneData vs the private LevelDto inside Level.Serialize) even though the design goal is a single conceptual structure that both the IDE and the core can use.

There is no first-class SceneSettings object, so there is nowhere clean to put avatar references, controller references, game-mode or input bindings.

Unsaved changes that exist only in the live Level / SceneEditorPanel have no guaranteed serializable in-memory path that is always handed to the engine on Play when the project has never been saved, or when the user has made changes since the last save. This is required: the SceneEditorPanel must be able to send its current (possibly unsaved) state to the engine.

Consequently the “Add to scene” button and the Properties panel still lack a clear, correct target for scene-level configuration data.

The main goal of the present work is therefore to introduce SceneSettings under the Scene, keep Level strictly as world content, make the transfer and loading path (including the in-memory unsaved state) reliable so that Play always receives the latest editor state, and keep the entire design composition-based so a scene that needs no player simply leaves the settings null.

The same compositional principle that is now being applied to the context menu is the foundation required for every subsequent editor feature that must remain cleanly separated from the core. Player spawn state is the next major data surface that will rely on it. A Level (or an associated ProjectSettings object owned exclusively by the IDE) will eventually hold an optional, serialisable description of the initial player state: preferred spawn points, default camera mode, which PlayerController / CameraController implementation the IDE has chosen to inject, which animation packs are attached to the player avatar, and the same information for any computer-controlled AI characters. When that description is present it is materialised into the Level payload that is already handed to RuntimeGameplayScene through the existing base64 command-line path; when it is absent the runtime simply leaves the FlyCameraController and the default PlayerMovement systems untouched. No core class ever inspects ProjectSettings or assumes the existence of a spawn configuration.

Because the configuration is pure data, the PropertiesPanel becomes the natural place to edit it. The same generic context-menu infrastructure we are completing today will later let a user right-click an avatar or AI entry and choose “Add Animation Pack”, “Set as Default Spawn”, or “Assign Controller”. The panel itself will request a context menu by supplying a list of labels and data-hooks; the core will remain oblivious to the meaning of those hooks. Parallel work will introduce a lightweight Project Settings form (still an IDE-only panel) that surfaces the same data objects for global defaults, and a Spawner component whose configuration is likewise edited through the PropertiesPanel and serialised into the Level. All of these features share the identical contract: the IDE composes the data, the core only consumes a neutral Level / SceneData payload, and any missing configuration is treated as “use the engine defaults”.

This disciplined separation guarantees that the runtime process stays a clean, isolated replica of a shipped game, while the editor continues to feel like a living meta-game in which creators can attach animation packs, redefine spawn behaviour, or swap camera controllers without ever touching engine source. The generic, data-driven context menu is therefore not an isolated UI convenience; it is the first concrete realisation of the composition pattern that will keep every future PropertiesPanel extension, project-settings surface, and spawner authoring tool safely on the IDE side of the boundary.
