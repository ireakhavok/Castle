Scene Protection Options for SiegeEngine
Future Development Reference
Date: April 28, 2026

================================================================================
OVERVIEW - THE PROBLEM
================================================================================

Current state:
- Scene data lives in external .scene.json files under <project>/Scenes/
- project.json contains metadata + references to scenes
- On export, we copy these files to a Game/ folder for shipping

The core issue:
- Any external file the user can reach can be edited or deleted.
- Even a "protected_scenes.manifest" next to the EXE is bypassable:
  * User opens it in Notepad and removes entries
  * User deletes the manifest entirely
  * User hex-edits the scene JSON to flip IsProtected = false

Requirement for real protection:
- Protection decision + verification data MUST be embedded inside the final game binary (EXE).
- Once compiled into the EXE, the user cannot change it without decompiling and recompiling the entire game (non-trivial).

================================================================================
OPTION A - SIMPLE EMBEDDED HASH LIST (RECOMMENDED FOR V1)
================================================================================

Concept:
- On "Export Protected Game", for every scene marked protected:
  * Compute SHA256 hash of the final .scene.json content
  * Store sceneName → hash in a generated C# source file
- That file is compiled into the EXE as a static readonly Dictionary
- At runtime, SceneManager checks: if scene is in the dictionary, the on-disk file must match the baked hash

How it works at export time:
1. Developer marks scenes as "Protected" in editor UI (checkbox)
2. Export command:
   - Copies project to Game/ folder
   - For protected scenes: computes final hash
   - Generates ProtectedSceneHashes.cs:
       internal static class ProtectedSceneHashes {
           public static readonly Dictionary<string, string> Hashes = new() {
               ["Main"] = "a3f2c8e9d4b1...",
               ["BossFight"] = "7e9f1a2b3c4d..."
           };
       }
   - Adds the generated .cs file to the game project
   - Compiles the final EXE (with hashes baked in)
3. Shipped game contains the hash list inside the binary

Runtime check (SceneManager.cs):
- Before loading a scene, check if sceneName exists in ProtectedSceneHashes.Hashes
- If yes: compute current file hash → compare to baked value
- Mismatch → refuse load or load safe fallback

Pros:
- Very simple to implement (one generated .cs file + one runtime check)
- No key management for the developer
- Still catches 99% of casual tampering
- Fast to build and test
- Easy to understand and debug

Cons:
- Not cryptographically strong (user could theoretically replace the entire EXE with a modified version)
- No way to prove "this file came from the original developer"
- If someone decompiles the EXE they can see the expected hashes

When to use:
- Default for hobbyist / single-player / creative games
- First version to ship (fastest path to working protection)
- Later upgrade path to Option B when you need stronger guarantees

================================================================================
OPTION B - FULL CRYPTOGRAPHIC SIGNING (RSA / ECDSA)
================================================================================

Concept:
- Use asymmetric cryptography (private key signs, public key verifies)
- Developer keeps private key secret
- Game ships with public key + signatures embedded in EXE
- Tampering invalidates the cryptographic signature

How it works:

Key generation (one-time, on first protected export):
- Auto-generate 2048-bit RSA key pair using System.Security.Cryptography
- Save private_key.pem in project root with strong warning:
  "KEEP THIS FILE SAFE. NEVER COMMIT IT TO GIT. NEVER SHARE IT."
- Public key is embedded in the game

Export flow:
1. Developer marks scenes as Protected
2. Export command:
   - Copies project to Game/ folder
   - For each protected scene:
     * Compute SHA256 of .scene.json
     * Sign the hash with private key → produce signature (base64)
   - Generate ProtectedSceneData.cs containing:
       - Public key (as byte[] or PEM string)
       - Dictionary<string, string> sceneName → signature
   - Compile into final EXE

Runtime verification (SceneManager.cs):
- Load scene JSON
- Compute its SHA256
- Look up signature in embedded dictionary
- Use public key to verify (signature, hash)
- Invalid signature → refuse to load

Pros:
- Cryptographically strong (industry standard)
- Even if user decompiles the EXE and sees the public key, they cannot create valid signatures without the private key
- Future-proof: can add key rotation, multiple signers, expiration, revocation lists
- Provides non-repudiation (proof that the file came from the developer)
- Matches how Steam Workshop, DLC, and many AAA titles protect content

Cons:
- Slightly more complex (key generation, signing, verification code)
- Developer must keep private_key.pem safe (we can add .gitignore entry automatically)
- One extra step on first export (key generation)
- Slightly larger EXE (public key + signatures are ~200-300 bytes per scene)

When to use:
- Competitive multiplayer games where cheating via scene editing is a real concern
- Commercial releases where you want maximum protection
- Any game where you want to be able to prove "this content is official"
- Long-term target once Option A is proven stable

================================================================================
RECOMMENDATION
================================================================================

Phase 1 (now):
- Implement Option A (simple embedded hash list)
- Add "Protect this scene" checkbox in SceneEditorPanel / NewTerrainPanel
- Add "Export Game" command in MenuCommands that bakes hashes
- Runtime verification in SceneManager

Phase 2 (later, when anti-cheat needs increase):
- Upgrade to Option B (RSA signing)
- Add automatic key generation on first protected export
- Store private key in project root with .gitignore
- Extend the generated .cs file to include public key + signatures
- Keep Option A as fallback for non-protected scenes

This phased approach lets you ship working protection quickly while leaving a clean upgrade path to full crypto.

================================================================================
IMPLEMENTATION NOTES (BOTH OPTIONS)
================================================================================

Files that will change:
- SiegeEngine.Core.Definitions/SceneData.cs          → add bool IsProtected { get; set; } = false;
- Keystone/ProjectData.cs                            → add Dictionary<string, bool> ProtectedScenes or similar
- CastleBuilder/BlueprintManager.cs                  → DoProjectSave() + new ExportProtectedGame() method
- CastleBuilder/MenuCommands.cs                      → add ExportGame() entry point
- SiegeEngine.Core.Managers/SceneManager.cs          → LoadScene() verification logic
- New file: Generated at export time → ProtectedSceneHashes.cs (or ProtectedSceneData.cs for Option B)

UX flow (both options):
1. In Scene Editor, each scene has a "Protect from tampering" checkbox
2. When checked, scene is added to protected list in project.json
3. Menu → File → "Export Game..." opens a small dialog:
   - Output folder (default: next to project)
   - "Include protection" checkbox (defaults to true if any scenes are protected)
   - "Build standalone EXE" option
4. On export:
   - Generate the protection .cs file
   - Compile final game (we can call msbuild or dotnet publish)
   - Copy assets + .scene.json files
5. Developer distributes only the Game/ folder (EXE + assets)

Runtime behavior:
- Protected scenes: any mismatch → log warning + load safe fallback or refuse
- Non-protected scenes: load normally (full mod support)
- Server can also re-verify hashes/signatures on player connect for extra safety
