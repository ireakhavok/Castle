The goal is to refine the launcher logic and build configuration in a way that emphasizes a dynamic, user-facing hub for mode selection without relying on command-line flags. The launcher, handled through Trebuchet/Launcher.cs, serves as the universal entry point for the app, initializing core components like IRenderContext, EventBus, and SteamEngine for networking and mods. It then presents a UI menu, built using the engine's HTML-parsed menus via UIOverlay.cs, allowing users to choose between playing a game, launching the IDE, or starting a new project. This approach keeps the launcher as part of the engine-core, making it lightweight and included in all builds, but fully overridable through mods or custom scenes.

In this setup, the menu options are designed for accessibility: "Play Game" loads a selected project or folder from saved lists or Workshop, running in runtime mode with SandboxScene.cs and core systems only, without panels or docks. "Launch IDE" loads the IDE layers from CastleBuilder DLLs, enabling PanelManager for windows and opening the editor scene with docks and panels. "Start New Project" triggers BlueprintManager.cs to scaffold a template like 3D FPS JSON, then transitions to IDE mode for immediate editing. The launcher checks UISettingsManager.cs for the last mode or project on start, defaulting to the menu if none is set, and includes a "Dev Tools" button in play mode to toggle IDE access if DLLs are present, promoting exposure without forcing it.

For build configuration, maintain a unified build process in Visual Studio with one EXE that handles all modes, branching internally based on runtime decisions from UI or config, such as if (config.IsIDEEnabled) LoadIDE(). The EXE includes core plus optional IDE DLLs copied to the output folder if an "IncludeIDE" toggle is set in csproj or ModManager config. Hobbyists can export with IDE included for the full app experience, where the launcher menu shows all options, while pros export without IDE DLLs for a leaner EXE that defaults to play mode. Devs can customize via project properties or scripts, like post-build copies of IDE DLLs if a flag file exists.

Devs opting out of the launcher or IDE can replace it in VS by creating a new Main.cs entry point that calls core directly, bypassing Trebuchet, or use mods as JSON overrides in ModManager to hide IDE options or reskin the launcher as their game's main menu, such as adding "New Game" instead of "Play." This encourages reuse of PanelManager for in-game windows like options menus as docked panels. For multiuser support in IDE mode, the launcher can join or host sessions via Steam lobbies, with changes synced through EventBus, but the setup ensures no forced IDE in games—players get a pure experience, with the launcher directly leading to play.

Saving remains consistent across setups, focusing on core-data only in JSON or XML for entities, scenes, and mods, with launcher or IDE state like open panels saved separately in user config via UISettingsManager.cs. This non-destructive approach avoids conflicts, allowing mods to extend saves while multiuser features merge changes with core validation. The overall plan empowers devs by positioning the launcher as a moddable core feature reusable for games, making the IDE optional yet discoverable, and keeping builds flexible without flags, leveraging UI and mod systems for better UX.
