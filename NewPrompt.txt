Hooks Concept Discussion
For integrating hooks like an FBX importer (or any engine feature), we could use fully-qualified namespace references such as "SiegeEngine.AssetParsing.FBXParser", where FBX parsing lives in SiegeEngine.AssetParsing with classes like FBXParser.cs). This keeps hooks modular and extensible—e.g., mods could override or extend them via JSON configs loaded by ModManager.cs. The idea is to treat hooks as bindings between HTML elements (e.g., a button in Desired_layout.html) and engine methods, similar to event handlers in native C# but triggered from parsed UI. No external imports; we'd build on existing abstractions like EventBus.cs for dispatching and IRenderContext for UI rendering.
To make it native (cshtml-like without web tech), the parser would scan HTML for attributes like data-hook="Namespace.Class.Method" on elements (e.g., <button id="ImportFBX" data-hook="SiegeEngine.AssetParsing.FBXParser.Load">), then map them to C# delegates/Actions. Invocation happens on user interaction (e.g., mouse click via MouseInputEvent in EventBus.cs), calling the hooked method with parameters (e.g., file path from UI state). This avoids web programming by rendering everything through your existing UIRenderer.cs or a new HtmlUiParser.cs, which generates UiElement quads/text and attaches hooks.
