+High-Level Suggestions for Fixing the Animation System
+After reviewing the provided files (FBXParser.cs, NodeParser.cs, FBXNode.cs, ModelComponent.cs, AnimationSystem.cs, FBXParserBase.cs, and related classes like FBXModel.cs, AssetViewerPanel.cs, and ModelManager.cs), I've synthesized the issues with the current implementation. The core problems stem from parsing inaccuracies (e.g., extraneous "armature" node treated as a bone), flawed hierarchy building (limbnodes misinterpreted as bones with incorrect lengths/positions), axis/scaling remapping errors, and incomplete animation application (e.g., no proper skinning in rendering, mismatched hierarchies for external animations). The visualization in AssetViewerPanel confirms keyframes are parsed but transforms are misapplied, leading to non-humanoid results.
+These suggestions prioritize modular, iterative fixes to align with engines like Unity (which uses Avatar for bone mapping) or Godot (joint-based skeletons with AnimationPlayer). We'll treat limbnodes as joints (not bones), compute bone visuals from joint positions, ensure Z-up Y-forward consistency, and enable animation blending on static skeletons. Changes will be minimal per iteration, focusing on stability.
+1. Exclude Extraneous Nodes like "Armature" During Skeleton Parsing
+
+Rationale: In FBXParser.BuildModelFromForest, modelNodes includes nodes with type "Root", which often captures container nodes like "Armature" (common in Blender exports). This adds an extra root bone, offsetting the hierarchy. UsedBoneIds filtering helps but doesn't exclude containers.
+Proposal: Add a name/type filter in modelNodes LINQ: exclude if Name.Contains("Armature") or type == "Null"/"Root" unless it's a true root (no parent, has limb children). Recursively build hierarchy only from valid LimbNode/Limb. This ensures skeleton.Bones starts from the actual root joint.
+Impact: Fixes extra bone; verify with a sample Blender FBX (e.g., humanoid armature).
+Verification: Log skeleton.Bones.Count and names; visualize in AssetViewerPanel should show correct hierarchy start.
+
+2. Refactor Bone vs. LimbNode Logic: Treat as Joints with Computed Lengths
+
+Rationale: Current Bone.ComputeLocal adds arbitrary offsets (e.g., Size/2 along Z for LimbNode), assuming bones have length, but FBX limbnodes are joints (positions only). Visualized "bones" are wrong because lengths are guessed, not derived from child joints. Animations move joints but not in humanoid proportions due to this.
+Proposal: Rename Bone to Joint; remove BoneType-specific offsets in ComputeLocal. Compute visual "bone" lengths dynamically in UpdateSkeletonVisualization (AssetViewerPanel) or a new SkeletonVisualizer class: for each joint, draw lines to children using global positions (from _currentGlobalTransforms). If no child, use Size property or default (e.g., 0.1f) along local forward. For rendering, apply skinning in shader (already in AssetShader) using finalTransforms.
+Impact: Aligns with joint-based systems; fixes non-humanoid visuals.
+Verification: Load a humanoid FBX; check if visualized skeleton matches expected armature (e.g., arms/legs proportional).
+
+3. Improve Axis Remapping and Scaling Consistency
+
+Rationale: RemapVector/RemapRotation apply sourceToTarget/signs, but globalSettings parsing assumes defaults (e.g., upAxis=1), ignoring file-specific coords. ModelScale = unitScaleFactor/10 assumes cm-to-m, but FBX can vary. Positions are scaled, but rotations/orders may flip incorrectly, causing distorted animations in Z-up space.
+Proposal: Make remapping functions take globalSettings params dynamically. Add post-parse normalization: compute scene scale from OriginalUnitScaleFactor, apply uniformly. For rotations, use Quaternion for remapping instead of Euler to avoid gimbal issues. Test with known FBX exports (e.g., Blender Y-up vs. engine Z-up).
+Impact: Fixes mismatched positions/lengths; ensures animations play correctly in engine coords.
+Verification: Compare bone positions before/after animation frame; they should match a reference tool like Blender.
+
+4. Enable Applying External Animations to Static Models
+
+Rationale: AnimationSystem assumes model.Animations are loaded with the mesh, but static models lack them. LoadAnimation (in AssetViewerPanel) remaps by name but doesn't validate hierarchy, leading to partial mapping (e.g., missing bones). No blending or state machine.
+Proposal: Add Skeleton.MatchAndApplyAnimation(Animation externalAnim) to map by bone name, fallback to index if names mismatch, log unmapped bones. In ModelManager, separate LoadMesh and LoadAnimations methods. Add AnimationComponent properties for blending (e.g., float blendFactor). In AnimationSystem.Update, interpolate between current/ target anim if blending.
+Impact: Allows static model + external FBX anim; modular like Godot's AnimationPlayer.
+Verification: Load static humanoid, apply walk anim; check if all bones animate (log unmapped).
+
+5. Enhance Debugging and UX in AssetViewerPanel
+
+Rationale: Current visualization draws lines but uses guessed directions (e.g., Z-up for LimbNode), ignoring actual child positions. No controls for bone selection/debug info.
+Proposal: In UpdateSkeletonVisualization, iterate hierarchy: for each joint, get global pos, draw sphere (add point rendering), and lines to children. Add UI dropdown for anim selection, sliders for time/ speed. Log decompose failures in GetBoneTransforms.
+Impact: Makes debugging intuitive, like Unity's preview window.
+Verification: Play anim; skeleton should deform human-like, with text overlays showing pos/rot.
