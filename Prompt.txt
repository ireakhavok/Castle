Vision & End Goal
SiegeEngine is a custom C# game engine purpose-built for real-time multiplayer MMORPG-style experiences. It was designed from the ground up with moddability, extensibility, and security as core pillars. The engine supports hundreds of concurrent players through authoritative server validation, client-side prediction, reconciliation, entity delta compression, spatial partitioning, frustum culling of sensitive data, and ray-cast occlusion checks for anti-cheat protection.

A defining philosophy is that the entire IDE/editor (Castle) is built directly on top of the game engine itself. This makes the tool self-hosting and self-moddable: every system used to run games is also used to build them. Creators — solo hobbyists, small teams, or large communities — can create, mod, share, and play custom games with minimal friction. Game development itself becomes an engaging “meta-game” where intuitive tools, seamless live previews, and instant testing keep builders fully immersed.

Architecture Overview
The system is cleanly layered into four major concerns that remain strongly separated yet share the same core runtime, plus a fifth project layer that must never bleed into Core or IDE types:

Core Engine (SiegeEngine): Foundational systems used by both gameplay and the editor. Abstracted rendering pipeline (OpenGL today with paths for DirectX/Vulkan), mature FBX asset pipeline (meshes, skeletons, animations, bones, materials, textures), Entity/Component architecture with parenting and delta tracking, central EventBus with strongly-typed networked events, GameSystem classes, Scene management, production-grade HTML/CSS/JS UI framework, mod loading, Steam-based networking, custom physics, GPU compute acoustics, lighting/shadows, and post-processing.

Editor / IDE Layer (Castle): Runs the engine in editor mode. Dockable/resizable panels with snapping, live updates, and pop-out windows. Context blades switch editing modes (Terrain, Animator, Scene Editor, Configuration). Project/scene/blueprint management lives here only.

Server Layer (Citadel): Fully authoritative gameplay logic — server-side validation, spatial grids, occlusion testing, movement/inventory/combat checks, entity delta tracking, efficient network broadcasting. Same server code runs dedicated, hybrid, or editor-collaboration.

Bootstrap / Launcher Layer (Trebuchet + Foundation): Unified startup, Steam init, mod discovery (local + Workshop), context creation, settings, panel/scene orchestration, main loop. Program.cs parses Play/Export args and hands payloads to core SceneManager only.

Project Layer (Siege_Engine_Example_Projects, and any user project folder): Persistence on disk (project.json + Assets/ + Scripts/). Project scripts compile to a project assembly loaded at Play/Export via ScriptLoader. Project code may use public Core APIs (GameSystem, Scene, PlayerMovement, EventBus, IPanel contracts) and may register custom scenes / player controllers / future dynamic panels. Project code must never reference CastleBuilder, Keystone, ToolChest, MapRoom, ReadingChamber, ProjectSettings, or any other IDE type.

Key Design Principles
- Strong separation of concerns between core engine code, editor-specific logic, and project scripts.
- EventBus + strongly-typed IEvent system (with serialization) is the single source of truth for all communication — UI ↔ code, client ↔ server, editor ↔ runtime, mod hooks, and project-script hooks.
- Modding is first-class: mods can override or extend any system through JSON configuration and fully-qualified hooks without conflicts.
- The custom UI framework (HTML/CSS parser + JS context + data-hook system) powers both in-game UI and the entire editor and is designed to be production-grade and easily extensible.
- Networking supports pure P2P, hybrid authoritative, and dedicated server modes from the same codebase.
- All major systems (rendering, assets, events, UI, scenes) are deliberately shared between runtime and editor so the tool is inherently self-moddable.
- Project scripts are the third boundary. Showcase work (inventory, board games, custom controllers, dynamic docking panels) belongs in the example-project repo unless a missing Core contract must be added first.

Absolute boundary rules
IDE layer (CastleBuilder + BlueprintManager + MenuCommands + ProjectSettings/Keystone + ToolChest/MapRoom/ReadingChamber panels) may freely read/write disk, call BlueprintManager.SaveCurrentProject, open panels, and emit payloads.

Core files (SiegeEngine + Foundation + Trebuchet/Launcher + RuntimeGameplayScene + SceneContext) may never read ProjectSettings, Keystone, or any IDE type directly. They may only receive serialized Level/SceneData via command-line / payload-file args or SceneContext objects composed entirely inside core. They may load project assemblies through ScriptLoader using paths supplied at launch.

Project files (example-project Scripts/, project.json, Assets/) may never reference IDE namespaces. They consume Core public contracts only. Dynamic panels contributed by a project must register through a Core panel/hook contract, not by constructing CastleBuilder panel types.

This guarantees the runtime process is a clean, isolated replica with zero IDE bleed, and that a shipped game does not carry the editor.

Data management rule
Level is the single source of truth for gameplay state (entities, terrain, skybox, environment, customData, lighting/post-process settings that belong to the level). Project folder on disk (project.json + Assets/ + Scripts/) is only for persistence, script compile, and Export. Play mode must be 100% in-memory from the payload + ctx path (plus loaded project assemblies). Export mirrors the same payload path but adds full asset copy + starting JSON manifest + compiled scripts. No runtime snapshot files, no extra loader classes, no guard clauses that bypass ctx, no direct disk reads inside core — only the payload + ctx composition + ScriptLoader assembly list.

How Play / Export / Launcher / Program.cs satisfy these rules
PlayGame/ExportGame in MenuCommands.cs (IDE side) saves via BlueprintManager, builds project scripts via ScriptLoader.BuildProjectScripts / CopyProjectScripts, constructs the Play payload (BlueprintManager.BuildPlayPayloadFile — Level + SceneData), then Process.Start Foundation.exe with --client --play-project and the payload args. Launcher.Start and Program.Main parse those args safely, call ScriptLoader.LoadCustomAssemblies, and hand payloads to SceneManager.SwitchToRuntimeGameplay (pure core). SceneManager deserialises into Level, creates SceneContext with CurrentLevel populated, and RuntimeGameplayScene.LoadContentFromContext rehydrates entities/terrain/skybox from ctx only. Export adds the asset-copy + script-copy step after the same payload construction. Saving/loading stays IDE-only. Play/Export stay payload-only. Core stays ctx-only. Project assemblies stay attribute/hook-only.

Treat this as the immutable foundation.
