PROJECT CONTEXT – SiegeEngine / CastleBuilder (May 2026)
Vision & End Goal
SiegeEngine is a custom C# game engine built for MMORPGs that prioritizes moddability, extensibility, and security from the ground up. The engine supports real-time multiplayer with hundreds of players, strong client prediction, authoritative server validation, reconciliation, frustum culling of sensitive data, ray-cast occlusion checks, and other anti-cheat measures.
A core philosophy is that the IDE/editor is built on top of the engine itself (CastleBuilder). This makes the entire tool self-moddable and self-hosting. The engine and editor share the same core systems (rendering, events, UI, assets) but maintain heavy separation of concerns between core engine code and IDE/editor code.
The ultimate goal is to empower solo hobbyists, small teams, and communities to build, mod, share, and play custom MMORPG-style games with minimal friction — treating game creation itself as an engaging “meta-game.”
Architecture Overview

Core Engine (SiegeEngine/): Rendering (OpenGL via Silk.NET/GLFW, but abstracted for swapping between that and directx or vulkan), asset pipeline (mature custom FBX parser for meshes, skeletons, animations, bones, materials), Entity/Component system (traditional OOP components), EventBus + strongly-typed IEvent (central communication backbone for UI ↔ C#, client ↔ server, editor events, etc.), GameSystems, Scenes, custom HTML/CSS/JS UI framework, mod loading, Steam networking.
Editor / IDE (CastleBuilder/, ToolChest/, MapRoom/, Keystone/, ReadingChamber/): Dockable/resizable IDE panels, context switching (terrain, scene editor, animator, etc.), BlueprintManager, project/scene management, asset browser, properties inspector, brush tools, animation timeline, etc. Built directly on top of the engine’s UI, events, and rendering.
Server (Citadel/): Authoritative GameServer, ServerValidationSystem, EntityDeltaTracker, spatial grid, occlusion, movement/inventory/combat validation, delta compression.
Launcher / Bootstrap (Trebuchet/, Foundation/): Launcher.Start() → initializes contexts, EventBus, ModManager, MenuPanel, SceneManager, PanelManager, etc.
Other folders (MapRoom/, ToolChest/, etc.): Specific editor scenes and panels.

Key Design Principles

Strong separation of responsibility between core engine and editor/IDE code.
EventBus + IEvent (with Serialize/Deserialize) is the single source of truth for all communication.
Modding is first-class: mods can override/extend via JSON configs + fully-qualified namespace hooks (e.g. SiegeEngine.AssetParsing.FBXParser.Load). Mods load from local mods/ directory and Steam Workshop.
The custom UI system (HTML/CSS parser + JSContext/JSEvaluator + DataHook system) is production-grade and will be used for both editor and in-game UI. It is very feature-rich; extension (Lua, full V8, etc.) is planned but not immediate priority.
Networking supports pure Steam P2P, hybrid authoritative server, and dedicated server as distinct options.
Unity asset interop (UnityAssetLoader, meta files, prefabs) is deprecated and not actively developed.

Core Game Breakdown (SiegeEngine + shared core folders)
The game (and editor) boots through a single, unified pipeline in Trebuchet/Launcher.cs → Launcher.Start(...). This is the true entry point (called from Foundation/Program.cs Main). Bootstrap first loads UISettingsManager (window size, renderer choice, fullscreen), initializes SteamEngine + ModManager (local + Workshop mods), creates EventBus and ContextManager (OpenGLContextManager → GLFW + OpenGL render context), then instantiates InputHandler, MenuPanel (main menu UI), PanelManager, and SceneManager. Optional dedicated-server or P2P-lobby logic runs here. The main loop then drives _controlContext.PollEvents(), Scene.Update + GameSystems.Update, PanelManager.Update (input routing, docking, resizing), Scene.Render + PanelManager.Render, and buffer swap. Scene lifecycle is managed by SceneManager.OnSwitchScene, which disposes the current scene, creates a new one via SceneRegistry, and calls Initialize(width, height). Every frame executes Update(deltaTime) → systems → player/camera → Render(entities). Server/multiplayer lifecycle is handled in Citadel: ServerProgram.Main spins up GameServer (authoritative or editor mode), NetworkManager + Steam P2P manages send/receive, and GameServer.Update drives validation, delta compression, and broadcast. Client-side uses ClientGameServerProxy for local prediction/reconciliation. Shutdown cascades Dispose through scenes, panels, renderers, textures, buffers, and Steam.
Core systems are tightly coupled yet shared with the editor. Rendering is abstracted via GameRenderer, ModelRenderer, BackgroundRenderer, LayeredUIRenderer, VertexBuffer, and a family of *Shader.cs classes; it handles OpenGL drawing of models, animations, terrain, and UI with projection support (perspective/ortho) and frustum culling. The asset pipeline (FBXParser family, ModelManager, TextureLoader, CustomTerrainParser, GeoTiffParser) loads meshes, skeletons, animations, bind poses, textures, and heightmaps on-demand with caching, feeding ModelComponent and Entity. Entity/Component uses Entity + IComponent derivatives (PhysicsComponent, ModelComponent, AnimationComponent, TransformComponent, etc.) for parenting and delta tracking, all managed by GameServer or ClientGameServerProxy and driven by events. EventBus + strongly-typed IEvent (with Serialize/Deserialize) serves as the single source of truth for UI↔C#, client↔server, editor↔runtime, and mod hooks. GameSystem base classes (AnimationSystem, PhysicsSystem, AudioSystem, LightingSystem, PlayerControllerSystem, ClientPredictionSystem, etc.) run per-frame updates and server-authoritative validation. Input and camera flow through InputHandler, CameraController/FlyCameraController/AngledOrthoCamera, Player, and PlayerMovement, producing MovementRequestEvent that is reconciled on the server. Networking (SteamEngine, NetworkManager, ClientGameServerProxy) supports P2P, dedicated, and lobby modes with serialized events. The UI framework (UIOverlay, HtmlElement derivatives, CssParser, JSContext/JSEvaluator, DataHookProcessor) powers both in-game and editor interfaces. Modding via ModManager makes overrides first-class. Security/anti-cheat features in Citadel.Server include ServerValidationSystem, EntityDeltaTracker, spatial grid, occlusion ray-traces, and authoritative movement/inventory/combat checks.
IDE / Editor Breakdown (CastleBuilder + ToolChest + MapRoom + Keystone + ReadingChamber + shared editor pieces)
The IDE is the engine itself running in editor mode (GameServer with isEditor = true). Lifecycle begins in the same Launcher.Start but immediately enters editor context, typically showing the MenuPanel. Context switching is orchestrated by MenuCommands.cs + ContextManager + ProjectSettings: calls such as SwitchToTerrain, SwitchToSceneEditor, or SwitchToAnimator fire ContextChangedEvent, which IDEUIOverlay.OnContextChanged handles by refreshing menus and loading the appropriate scene (TerrainCreatorScene, TwoDCreatorScene, EditorScene, etc.) via SceneManager. Panel lifecycle is centralized in PanelManager: OpenPanelEvent / ClosePanelEvent drive AddPanel / RemovePanel; panels (NewProjectPanel, SceneEditorPanel, PropertiesPanel, AssetBrowserPanel, TreeViewPanel, etc.) inherit BasePanel/UIOverlay and are managed by one of three docking strategies (DesktopDockingStrategy, DynamicDockingStrategy, IDEDockingStrategy) with saved layouts via ProjectLayoutManager. Resize, drag, focus, and scroll are routed centrally; CaptureManager handles modal input capture. Project and scene management lives in BlueprintManager, ProjectSceneCache, and ProjectSettings: NewProject/LoadProject/SaveProjectAs events open panels, ProjectSceneCache stores GameScene + Level per name (with proper Dispose on unload), and BlueprintManager ensures default scenes while handling save/load hooks. Editor-specific scenes provide the interactive canvas—T TerrainCreatorScene drives brush sculpting, ghost preview, heightmap I/O, and TerrainModifiedEvent; TwoDCreatorScene handles sprite placement with ortho camera; ModelViewerScene offers animation preview, blend-stack testing, and skeleton visualization; SceneEditorPanel + SelectionBoxOverlay enable entity placement and selection. Tool panels in ToolChest (AssetBrowserPanel, PropertiesPanel, TreeViewPanel, AnimationTimelinePanel, AnimationBlendPanel, BrushPanel, ConsolePanel, etc.) all use the HTML UI system plus data hooks (HandleDataHook) routed through DataHookProcessor to C# manager methods via reflection. Custom overlays (ICustomOverlay implementations such as SelectionBoxOverlay, PlacementOverlay, BlendDotOverlay) allow in-panel 3D drawing for ghosts, selection boxes, and blend previews.
Core IDE concepts enforce strong separation of concerns while remaining self-hosting. The entire editor runs on the engine’s rendering, UI, events, and asset systems, making it a first-class “meta-game.” Context-aware behavior is driven by Keystone (OutlinerCoordinator, ProjectLayoutManager) and CastleBuilder.Events (ContextChangedEvent, LoadProjectEvent, etc.), which keep menus and panels synchronized. The dockable panel system (PanelManager + the three strategies) supports floating, tabbed, and persistent layouts. Data hooks and the JS bridge allow UI elements to declare data-hook attributes that DataHookProcessor turns into reflection calls, while JSContext provides full interactivity. Asset-centric workflow flows from (now-deprecated) UnityAssetScanner through modern FBX and custom terrain pipelines into AssetBrowserPanel and ReadingChamber tools. Blueprint/Project model (BlueprintManager + ProjectSceneCache + ProjectSettings) manages scenes, levels, unsaved heightmaps, and layout state. Editor collaboration readiness is already present: events such as EntityPlacedEvent and TerrainModifiedEvent are network-aware, and GameServer in editor mode can support real-time multi-user editing (WIP). Throughout, editor folders (CastleBuilder., ToolChest., MapRoom., Keystone., ReadingChamber.) consume only core APIs via events, managers, and scenes—never mixing editor-specific logic into SiegeEngine. packages—while the isEditor flag on GameServer toggles validation and authorization behavior. This architecture keeps the foundation rock-solid for future extensibility and moddability.

Current State & Priorities

Core rendering, asset pipeline (FBX), event system, mod loading, server validation, and terrain editor (brush sculpting, heightmaps, ghost preview, wireframe/textured modes) are solid and production-ready.
Panels and overall editor efficiency feel great.
WIP areas (next focus): Solidifying clean editor vs runtime separation (especially CameraController and PlayerMovement), client prediction + reconciliation, real-time multiplayer editing collaboration, entity replication maturity, and continued new feature development on a rock-solid foundation.
